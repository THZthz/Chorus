## 0. Invariants (unchanged, verbatim)

1. `state` is a fold of the append-only log; `fold(loadLog(saveLog(log)))`
   equals the played state byte-for-byte, **including the in-flight window
   table** (a log may legitimately end with open windows).
2. Concrete log rows round-trip: `format(parse(row)) === row`. The broad
   assertion is play-driven (`test/nightjar-explorer.test.ts:75-89`), so new
   engine-written kinds are auto-covered; each new kind also gets one
   targeted law-2 test on a row captured from a real run
   (precedent: `test/dice.test.ts:527-531`).
3. The engine never re-derives randomness or arithmetic at replay.
4. Steps and advance passes are atomic: application failure → rejected,
   nothing logged. **[amended, C-synthesis]** A failure while applying a
   window's outcomes *during a pass* refuses that WINDOW (complete row with
   the REFUSE marker; fold no-ops it via the existing §6.5 rule) instead of
   rejecting the pass — otherwise the pass rolls back, the window stays open,
   and every future advance re-fails forever (livelock).
5. No RNG outside the recorded-counter mechanism.
6. Draft discipline covers the new state: `cloneState` deep-copies the window
   table **entry-by-entry** (windows hold Ref arrays; a shallow `new Map`
   would leak draft mutations into real state — the byName precedent,
   types.ts:91-92).

## 1. The model: verb stations with parallel windows

- A committed action **begins a window** `[T, T + Σdurations]` (minutes) on
  its verb's **station**. Several stations may overlap in game time.
- **Station exclusivity**: a verb with an open window rejects a new window of
  the same verb. Different verbs run freely in parallel.
- **Card locks**: any card bound to an open window (in ANY role) is busy — a
  new step binding it is rejected, naming the holding verb and its end clock.
  Rejections log nothing.
- **Events do not respect locks**: triggers/expiries may destroy a locked
  card. At completion, bindings re-resolve; dead refs are **dropped from the
  binding** (deterministic, documented); the outcome list still applies.

## 2. Time is explicit — and minute-precise **[amended, C7]**

- `Step` carries `startMin: number` (absolute minutes). The `Clock` type is
  halfhour-quantized and cannot represent "start now" when `state.now` sits
  mid-halfhour (durations like 20m put it there); the default start clock is
  `state.now` itself. Typed clock input (`1:12 @ …`) stays the quantized
  input syntax; `tGame` on records remains display-only `formatClock`.
- Committing with default clock begins at `now` and moves nothing. An
  **explicit future clock** first runs one advance pass to it, then begins.
  The monotonic guard (`engine.ts:148`, minutes) is unchanged — BEGINs can
  never start in the past.
- A **bare clock input** (`1:12` alone) is a pure advance: resolve everything
  due up to that minute. **[amended, C7]** Today this input CRASHES
  (`suggestVerb(undefined)` TypeError, lenient.ts:75→172, uncaught through
  handleLine and both TUI call sites) — fixed here by an early return right
  after the clock lex (lenient.ts:58) plus a regression test.
- WAIT stays a verb-window; an `ADVANCE` applying at completion **extends the
  ongoing pass's target** (loop until no more due work). **[amended, C9]**
  The extension must land in the pass's `wait` row span (`advancedMin`), never
  in a post-record `ctx.extraAdvanceMin` — fold replays ADVANCE rows into the
  inert counter and then overrides from recorded `advancedMin`
  (engine.ts:857-858), so a misrouted extension would silently vanish at
  save/load. Both authored uses (nightjar WAIT `till_dawn` 2h, DREAM `seal`
  30m) are preserved under this rule.

## 3. Records: action = BEGIN; new kinds complete, wait

| kind | carries | fold effect |
|---|---|---|
| `action` (BEGIN) | clauses, recipes (chosen at commit), outcomes = PROGRESS ticks, `advancedMin` = Σdurations (window length) | register the window; **clock untouched; outcomes not applied** (REFUSED rows stay no-ops per the kind-independent scan, engine.ts:829) |
| `complete` (new) | `beginId`, binding refs, concrete outcomes, `tGame` = completion clock (display/ordering) | remove the window; apply outcomes with `ctx.now` = **the window's start, read from the windows table via `beginId`** — missing window = loud fold error; clock untouched |
| `wait` (new) | `tGame` = span start, `advancedMin` = span length | `now = tGame + advancedMin` — the ONLY clock-moving row |
| `event` | unchanged | unchanged |

- **[amended, C14]** The completion anchor MUST NOT be derived from `tGame`:
  fold recomputes `expiresAt` from `ctx.now` (engine.ts:500/833), so play and
  fold must read the same start minute. Both read the windows table
  (`beginId`), play from memory, fold from the registered BEGIN row — same
  source, no divergence. `tGame` on a complete row is deliberately the
  completion clock for journal display; it never feeds mechanics.
- **[amended, C1]** `wait` spans partition time by construction: every pass
  starts at the current `now` and BEGINs move nothing, so spans are
  non-overlapping and log-ordered — repeating slot triggers cannot double-fire
  across overlapping windows.
- Canonical forms **[amended, C5]**: BEGIN rows are today's action sentences
  (PROGRESS already parses). COMPLETE: `1:42 @ COMPLETE READ -> …` — the verb
  is a raw name token (NOT `ref()`; verb lexemes are reserved and would throw
  at parse.ts:221), stored in the existing `trigger` field. WAIT:
  `0:42 @ WAIT 1h` — one `dur` token, span on a new optional `Sentence.spanMin`;
  the record side reuses `advancedMin`. Kind unions widen at sentence.ts:65
  and engine.ts:28; `COMPLETE` joins RESERVED_WORDS (verified collision-free);
  the WAIT branch must precede the action fallthrough (parse.ts:150-152).
- JSONL unchanged **[amended, C13]**: all record fields stay
  JSON-serializable; the ten kind-dispatch sites (engine ×6, render, play-undo,
  fold, format) are enumerated in the verification notes and each is handled.

## 4. Commit vs completion semantics

- **Recipe selection at commit**, against the post-advance state; ids ride
  the BEGIN row; at completion the ids are looked up in compiled content
  (drift = loud error). Selection is a pure read (C3).
- **Top-level REFUSE pre-pass at commit** (scratch draft): a recipe refusing
  at TOP LEVEL → refused action row exactly as today (zero time). Gates keep
  rejecting at the table. REFUSE inside IF bodies defers to completion, where
  the complete row logs the attempt and the fold no-ops it — the pinned
  semantics of `test/conditionals.test.ts:341` (the corpus's one live nested
  REFUSE) survive this deferral unchanged. **[amended, C4]** The earlier
  claim "every authored REFUSE is top-level" held only for scripts + seed;
  tests may nest by design.
- **Lock checks at commit**: card busy (any role, any open window) or station
  busy → rejected, nothing logged.

## 5. Resolution order (the determinism core)

`advanceTo(T)` walks minutes upward from `state.now` to `T` over one atomic
draft:

1. Due completions first: every open window with `end ≤ current minute`,
   ordered by `(endMin, beginRecordId)` — a total order.
2. Then that halfhour's slot events: authored triggers (declaration order),
   then expiries (`at ≤ boundary` rule preserved) from a snapshot hoisted
   outside the whole walk. The per-slot body is a pure function of
   `(state, absSlot, snapshot)` — factored out mechanically, event internals
   untouched (C8). Completions at minute m precede slot-m events.
3. One pass: completions created by this pass resolve at the NEXT advance.
4. Any completion failure refuses that window (§0.4); any OTHER failure
   rejects the whole pass, nothing logged.

Same input sequence → same log → same state: interleaving is a pure function
of commit order and window arithmetic; no wall-clock enters anywhere.
